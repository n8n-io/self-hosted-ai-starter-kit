# Self-hosted AI starter kit

**Self-hosted AI Starter Kit** is an open-source Docker Compose template designed to swiftly initialize a comprehensive local AI and low-code development environment.

* Pure docker compose service catalogue for n8n community and enterprise variants
* Multi service `*.n8n.localhost` dev domain strategy works cross-OS dependency free
* Generates `.env` configurations from `.env.template` files with randomized secrets
* Best-practice docker compose specs with production ready security linting
* Awesome dev experience with [n8n-starter](./packages/cli/) cli and [Tilt](https://tilt.dev/) toolkit

## Quickstart

```bash
# Install dependencies
pnpm install
# Build ./packages/cli
pnpm run build
# Run cli setup
# 1. Generate .env files from any .env.template file
# 2. Fill the secrets declared in the .env.json next to each template: random values once, hashes and links kept in step
# 3. Create the n8n-starter-public and n8n-starter-private docker networks if they don't exist
pnpm run setup
# Optional: pick N8N_VARIANT, N8N_ASSISTANT, AI_RUNTIME, AI_ENGINE, AI_GATEWAY, AI_MODELS and DOMAIN interactively
pnpm run config
# Optional: check the tool versions and that every .env file and both docker networks exist
pnpm run verify
# Run the tilt docker experience (Ctrl+C stops tilt and tears the services down)
pnpm run dev
```

Requirements: Node.js 24, Docker Engine 25.0 and Docker Compose 2.24 or newer, declared once as `REQUIREMENTS` in [requirements.ts](./packages/cli/src/utils/requirements.ts) and mirrored by the Prerequisites of [README.md](./README.md) and `engines.node` of the root [package.json](./package.json); `verify` checks them, Tilt (`>=0.37.7`) checks itself through `version_settings()` in the [Tiltfile](./Tiltfile).

All root scripts are thin wrappers, see [package.json](./package.json):

| Script | Runs |
| --- | --- |
| `setup`, `verify`, `config`, `models`, `secrets`, `reset` | the matching [n8n-starter](./packages/cli/) command (`pnpm run models read`, `pnpm run models select`, `pnpm run secrets read`, `pnpm run secrets set`) |
| `cli` | the bare [n8n-starter](./packages/cli/) with everything after the script name as its arguments (`pnpm run cli --help`, `pnpm run cli models read vllm --json`, `pnpm run cli tilt resources`) |
| `dev` | `tilt up` with the [Tiltfile](./Tiltfile), then `tilt down` once Tilt exits |
| `build`, `test` | `pnpm -r run build` / `test` across all workspace packages |
| `lint`, `lint:fix` | `pnpm -r run lint` / `lint:fix`: the scripts of [compose/package.json](./compose/package.json), [dclint](https://github.com/zavoloklom/docker-compose-linter) over the catalogue configured in [compose/.dclintrc](./compose/.dclintrc), then `lint:env` (no bare `${VAR}` interpolation) and `lint:healthcheck` (every service has a healthcheck) |

## Repository structure

```text
.
├── Tiltfile                  # Tilt orchestration of every compose spec
├── .env.template             # Root configuration: N8N_VARIANT, N8N_ASSISTANT, AI_RUNTIME, AI_ENGINE, AI_GATEWAY, AI_MODELS, DOMAIN
├── .vscode/                  # Workspace settings: icons, file nesting, YAML custom tags, recommended extensions, mcp.json
├── assets/                   # Images, icons (the vscode-icons custom folder icons) and other static assets
├── .mcp.json                 # Project MCP servers for coding agents: the n8n documentation (n8n-docs)
├── .agents/skills/           # Agent skills: compose-catalogue, n8n-starter-cli, tilt, n8n-upgrade, validate, troubleshoot, n8n-docs (product lookups)
├── .claude/skills/           # One symlink per skill into .agents/skills/, for Claude Code, which only scans this directory
├── .volumes/                 # Bind-mounted runtime data, mirrors the compose/ layout, gitignored, default of VOLUMES_PATH
├── compose/                  # Docker compose service catalogue, one directory per service
│   ├── package.json          # n8n-service-catalogue: the lint scripts, .dclintrc beside it
│   ├── proxy/                # Edge: traefik + docker-socket-proxy
│   ├── n8n/                  # n8n variants (dev, build, community, enterprise) + task runners
│   │   └── assistant/        # The sandbox and web search of the n8n Assistant, enabled by N8N_ASSISTANT
│   ├── storage/              # postgres, pgadmin, redis, redis-insight, garage (S3)
│   ├── services/             # qdrant
│   └── models/               # Model servers, one directory per AI_ENGINE and per AI_GATEWAY
│       ├── models.json       # The model catalogue of every engine, one DNS-label id per entry (models.schema.json for editors)
│       ├── models.cloud.json  # The cloud models offered for the n8n Assistant, nested under their provider (models.cloud.schema.json for editors)
│       ├── ollama/           # ollama: one server pulls every model of AI_MODELS
│       ├── vllm/             # vllm: one container per model of AI_MODELS
│       └── litellm/          # litellm: the gateway, one endpoint and key for every model of AI_MODELS
└── packages/
    └── cli/                  # n8n-starter: setup, verify, config, models, secrets, tilt, reset
```

### `compose/`

Each service lives in its own directory `compose/<group>/<service>/` holding:

* `docker-compose.yml` – the spec, with a top-level `name:` so every service is its own compose project.
* `README.md` – one or two sentences on what the software is and its role in this kit (which variant enables it, whether Tilt starts it on demand), then a link list in a fixed order: Homepage, Repository, Docker image (one line per image the directory pulls), Documentation, API reference, Releases; a label without a page is left out. A directory with variants or runtime flavours (`n8n`, `ollama`, `vllm`) lists them in one line each and links the canonical table here. Nothing else: features, configuration and deployment belong to the upstream docs and to this file.
* `.env.template` – only when the service has required values (secrets, pinned versions) or optional knobs a developer may change (see [Compose spec rules](#compose-spec-rules)). `setup` copies it to `.env` next to it. A `.env.json` beside it declares which keys are secrets and how `setup` fills them; a secret no container reads, such as the password behind a hash, goes into a `.env.secrets` beside the `.env` (see [Secrets](#secrets)).
* Service config files mounted into the container (`traefik.yml`, `garage.<DOMAIN>.toml`, …).
* Bind-mounted data does not live here: it sits in `.volumes/<group>/<service>/` at the repo root (gitignored). The spec reaches it through `${VOLUMES_PATH:-<relative path to .volumes>}/<group>/<service>/…` (e.g. `${VOLUMES_PATH:-../../../.volumes}/storage/garage/data` from `compose/storage/garage/`), so the default lives in the compose file and no `.env` is needed for it. `VOLUMES_PATH` always names the `.volumes` root, never a service folder; set it only to relocate all runtime data (see [Configuration](#configuration)).

Groups are named after their role from n8n's point of view: `proxy` is the edge, `n8n` the application, `storage` its data stores and their admin UIs, `services` supporting services (qdrant) and `models` the model servers with their gateway. Two directories deviate from one compose file per service: `n8n` holds a cascade of variant files selected by `N8N_VARIANT` (next section), of which only one runs at a time, with the service directory `assistant/` beside them ([the n8n Assistant](#the-n8n-assistant-n8n_assistant)), and `models` holds the model catalogue `models.json` and the cloud models of the Assistant, `models.cloud.json`, next to one directory per `AI_ENGINE` and per `AI_GATEWAY` ([engines and catalogue](#composemodels-engines-and-the-model-catalogue)).

### `compose/n8n/` variants

`N8N_VARIANT` picks one self-contained compose file (mapped by `N8N_VARIANT_CASCADE` in [tilt.ts](./packages/cli/src/commands/tilt.ts)). Each file extends the previous one with compose `extends`, so service configuration is written once:

| Variant | File | Adds |
| --- | --- | --- |
| `dev` | [docker-compose.yml](./compose/n8n/docker-compose.yml) | the base: one unlicensed `n8n` container in regular execution mode on SQLite (`DB_TYPE=sqlite`, the file lives in the `.n8n` volume, [database](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/database)) with the internal task runner (`N8N_RUNNERS_MODE=internal`, a child process of n8n: JavaScript Code nodes only, and deprecated: n8n 2.49.7 logs the deprecation at startup, next to the Python runner it cannot start in internal mode, [task runners](https://docs.n8n.io/deploy/host-n8n/configure-n8n/set-up-task-runners)) and the instance owner managed by env (`x-n8n-env-owner`, see [Configuration](#configuration)); no storage service at all |
| `build` | [docker-compose.build.yml](./compose/n8n/docker-compose.build.yml) | postgres (`DB_TYPE=postgresdb`) and the external task runner: `N8N_RUNNERS_MODE=external` on main and the `n8n-runner` sidecar, which also brings Python Code nodes; needs postgres |
| `community` | [docker-compose.community.yml](./compose/n8n/docker-compose.community.yml) | queue mode: `EXECUTIONS_MODE=queue` on main, an `n8n-worker` with its own `n8n-worker-runner`, and an `n8n-webhook` processor serving production webhooks at `hooks.<DOMAIN>` (main stops serving them, `N8N_DISABLE_PRODUCTION_MAIN_PROCESS=true`); needs redis |
| `enterprise` | [docker-compose.enterprise.yml](./compose/n8n/docker-compose.enterprise.yml) | the license (`N8N_LICENSE_ACTIVATION_KEY` required on main, worker and webhook processor); S3 binary data (garage), external secrets and multi-main are still to be wired up |

Rules of the cascade:

* The base holds only what every variant needs. A variant adds services or overrides values; it never has to remove anything, because an inherited env var cannot be unset through `extends`. The license, for example, exists only in the enterprise file, and postgres only from the build file: the base runs on SQLite and the build file overrides `DB_TYPE` and `N8N_RUNNERS_MODE`.
* YAML anchors (`x-*`) do not cross files. Reuse across files happens at the service level, either cross-file (`extends: {file, service}`) or chained within a file (`n8n-worker` extends `n8n`), never by re-declaring anchors.
* Anchors are named after what they configure (`x-n8n-env-owner`, `x-n8n-env-sqlite`, `x-n8n-env-runners-internal`, `x-n8n-env-postgres`, `x-n8n-env-runners-broker`, `x-n8n-env-queue`, `x-n8n-env-webhook-processor`, `x-n8n-env-license`), never after a variant: the number of settings groups grows independently of the number of variants.
* Inherited lists and maps merge (networks are unioned, labels and env are merged). The rare removal uses the compose `!override` / `!reset` tags: the worker sets `networks: !override [n8n-starter-private]`, `labels: !reset []` and `volumes: !reset []` so traefik never routes to it and it stays stateless. Both tags are registered as `yaml.customTags` in [.vscode/settings.json](./.vscode/settings.json) so the YAML extension does not flag them.
* Every variant file is a complete entry point. `docker compose -f docker-compose.<variant>.yml up` from `compose/n8n/` runs it without Tilt (see [Configuration](#configuration) for what a service needs), which makes the same files usable on a production host.
* A worker and its task runner are a 1:1 pair (the runner dials one broker host), so scale by adding pairs, not with `--scale`. Workers carry no `.n8n` mount; community nodes installed through the UI only exist on main unless `N8N_REINSTALL_MISSING_PACKAGES=true` is set on the worker.
* The runner sidecars mount [n8n-task-runners.json](./compose/n8n/n8n-task-runners.json) over `/etc/n8n-task-runners.json`, a copy of the launcher config of the `n8nio/runners` image with one change: the Code node allowlists `NODE_FUNCTION_ALLOW_BUILTIN`, `NODE_FUNCTION_ALLOW_EXTERNAL` (JavaScript) and `N8N_RUNNERS_STDLIB_ALLOW`, `N8N_RUNNERS_EXTERNAL_ALLOW` (Python) are moved from `env-overrides` to `allowed-env`, because the launcher only forwards listed variables to a runner and the image's `env-overrides` pin them to `crypto`, `moment` and nothing for Python. The defaults (curated lists, no third-party Python package since the image ships none) live in `x-n8n-env-runners-code-allow` of the build file and appear commented out in [.env.template](./compose/n8n/.env.template); the two JavaScript lists are repeated in `x-n8n-env-runners-internal` of the base file, where `dev` hands them to the internal runner as container variables (anchors do not cross files, so keep both copies equal), and Python Code nodes run only with the external runner from n8n 2.0 ([v2.0 breaking changes](https://docs.n8n.io/changelog/v20-breaking-changes)); `*` allows everything, third-party packages beyond the image's `moment`, `luxon`, `lodash`, `nanoid` need an extended runners image. The file mirrors the image, so on every `N8N_VERSION` bump diff it against `docker run --rm --entrypoint cat n8nio/runners:<version> /etc/n8n-task-runners.json` and carry over upstream changes. See [Set up task runners](https://docs.n8n.io/deploy/host-n8n/configure-n8n/set-up-task-runners#configuring-launcher-in-runners-container-in-external-mode) and the [task runner environment variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/task-runners).
* The webhook processor (`n8n-webhook`, `command: webhook`, extends `n8n`) receives production HTTP triggers (`/webhook/`, `/webhook-waiting/`, `/form/`, `/form-waiting/`, `/mcp/`) and enqueues the execution for a worker; the test paths (`/webhook-test/`, `/form-test/`, `/mcp-test/`) are only served by main. It starts no task runner, so it has no runner sidecar and scales with `deploy.replicas` (`N8N_WEBHOOK_REPLICAS`, default 1; keep 1 while an MCP Server Trigger is in use, its SSE connections need a single replica). It keeps both networks (traefik routes to it) and no `.n8n` mount. See [Enable queue mode › Webhook processors](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode#webhook-processors) and [MCP Server Trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-langchain.mcptrigger).
* [docker-compose.community.yml](./compose/n8n/docker-compose.community.yml) mirrors n8n's [withPostgresAndWorker](https://github.com/n8n-io/n8n-hosting/blob/main/docker-compose/withPostgresAndWorker/docker-compose.yml) reference. Deliberate deviations: the webhook processor is an addition to the reference, the worker has no `.n8n` volume, there is no `depends_on` on postgres and redis (they are separate compose projects; Tilt `resource_deps` and the restart policy cover start order), and services carry healthchecks with `service_healthy` conditions.

### The n8n Assistant (`N8N_ASSISTANT`)

`N8N_ASSISTANT=true` runs n8n with the [n8n Assistant](https://docs.n8n.io/deploy/host-n8n/configure-n8n/set-up-n8n-assistant) (the `instance-ai` module), which needs a model, a sandbox to run code in and a search provider for web search. It is no variant: it combines with every `N8N_VARIANT`, so it is one anchor of the base file and one compose project beside the cascade instead of a fifth file in it.

| Part | Where | What |
| --- | --- | --- |
| the toggle | `N8N_ASSISTANT` of the root `.env`, `false` by default | reaches the n8n compose files by interpolation like `DOMAIN` (`${N8N_ASSISTANT:-false}`), and the Tilt plan, which enables the services below |
| the n8n settings | `x-n8n-env-assistant` of [docker-compose.yml](./compose/n8n/docker-compose.yml) | `N8N_INSTANCE_AI_ENABLED` and `N8N_INSTANCE_AI_SANDBOX_ENABLED` follow the toggle; the model is `N8N_INSTANCE_AI_MODEL`, `N8N_INSTANCE_AI_MODEL_URL` and `N8N_INSTANCE_AI_MODEL_API_KEY`; the sandbox `N8N_INSTANCE_AI_SANDBOX_PROVIDER=n8n-sandbox`, `N8N_SANDBOX_SERVICE_URL` and `N8N_SANDBOX_SERVICE_API_KEY`; the search `N8N_INSTANCE_AI_SEARXNG_URL` |
| the model | `N8N_INSTANCE_AI_MODEL` and `N8N_INSTANCE_AI_MODEL_URL` of `compose/n8n/.env`, written by `pnpm run config N8N_ASSISTANT` | a cloud model as `provider/model` without a URL, or a model of `AI_MODELS` with the OpenAI compatible endpoint of its engine |
| the services | [compose/n8n/assistant/](./compose/n8n/assistant/README.md), compose project `assistant` | `sandbox-certs`, `sandbox-api` and `sandbox-runner-1` (the [n8n sandbox service](https://github.com/n8n-io/n8n-sandbox-service)) and `searxng`, registered always and enabled only by the toggle |

Rules of the Assistant:

* n8n runs without it. Every key of `x-n8n-env-assistant` is optional (`${VAR:-default}`), so no variant needs an Assistant value in `compose/n8n/.env` and a copy of `compose/n8n/` runs on a host that never heard of the sandbox. A compose profile cannot do this: compose interpolates the whole file, a `${VAR:?}` in a service of an inactive profile or in an unused anchor included; a profile adds a second service instead of changing `n8n`, so both would run; and `depends_on` a profiled service fails while its profile is off.
* The anchor sits in the base file, so every variant inherits it through `extends`, the worker and the webhook processor included, which load the `instance-ai` module too.
* `N8N_INSTANCE_AI_ENABLED` exists from n8n 2.47.0 ([configuration](https://github.com/n8n-io/n8n/blob/master/packages/%40n8n/instance-ai/docs/configuration.md)): unset, it means off on the Enterprise plan and on everywhere else ([release notes](https://docs.n8n.io/changelog/release-notes)), so the anchor sets it from the toggle: `enterprise` behaves like the other variants, and `N8N_ASSISTANT=false` switches the Assistant off instead of leaving it to the plan. A choice saved in the Assistant settings of n8n wins over the variable. An n8n older than 2.47.0 ignores it and has the Assistant on.
* The model has a default in the compose file, the one model name there. n8n takes an empty `N8N_INSTANCE_AI_MODEL` literally and so loses its own default, so the compose default cannot be empty: it is the first model of the first provider in [models.cloud.json](./compose/models/models.cloud.json), which is also n8n's own default from 2.48.0, and a test keeps the compose file, the commented knob of the template and the catalogue equal.
* `config N8N_ASSISTANT` writes the model literally, the toggle after it, so a failure leaves the Assistant off. A cloud model is `N8N_INSTANCE_AI_MODEL=<provider>/<model>` and an empty `N8N_INSTANCE_AI_MODEL_URL`; the prompt lists the providers and models of `models.cloud.json`, and any other `provider/model` given on the command line is written with a warning, since the catalogue recommends and n8n decides. A model of `AI_MODELS` is the name its engine serves it under and that engine's endpoint: the tag and `http://ollama:11434/v1` for ollama ([OpenAI compatibility](https://github.com/ollama/ollama/blob/main/docs/api/openai-compatibility.mdx)), the Hugging Face id and `http://vllm-<id>:8000/v1` for vllm. Only a model the engine serves on the runtime and `AI_MODELS` lists is offered; the gateway of `AI_GATEWAY` is never used.
* Literal values go stale. With the toggle on, a URL that names a model server of this kit (`ollama`, `vllm-<id>`) but fits no model of `AI_MODELS` on the current engine and runtime is refused: `config AI_ENGINE`, `config AI_RUNTIME` and `models select` warn and keep what they were asked to write, and `tilt resources` (so the Tiltfile) fails naming `pnpm run config N8N_ASSISTANT`, as it does for a stale `AI_MODELS` id. A URL of any other host is the user's own endpoint and is left alone, and so is everything while the toggle is off.
* The key of the model, `N8N_INSTANCE_AI_MODEL_API_KEY`, is an optional `prompt` secret (see [Secrets](#secrets)): the API key of the cloud provider, which the Assistant settings of n8n take as well; the `VLLM_API_KEY` for a vllm model, since vllm refuses a request without its bearer token; nothing for ollama. `config` names the `secrets set` command for the first two and never writes a secret.
* The key of the sandbox, `N8N_SANDBOX_SERVICE_API_KEY`, is a conditional link to `SANDBOX_API_KEYS` of `compose/n8n/assistant` (see [Secrets](#secrets)): `setup` fills it, the compose file reads it as optional and `verify` misses it only while the toggle is on.
* The services follow the stack of n8n's [one-line setup](https://docs.n8n.io/deploy/host-n8n/install-options/one-line-setup) and [Docker Compose guide](https://docs.n8n.io/deploy/host-n8n/install-options/install-using-docker-compose) with the catalogue's rules applied: `environment:` blocks instead of `env_file`, so each container gets only its own variables, and three generated secrets, each passed to the API and to the runner under the name that side reads. One release pins the API, the runner and the sandbox image (`N8N_SANDBOX_VERSION`, the one n8n's `get-n8n.sh` installs). The certificates are issued for the service names `sandbox-api` and `sandbox-runner-1`, which therefore must not change; the one-shot `sandbox-certs` writes them to `.volumes/n8n/assistant/tls`, joins no network, leaves existing ones alone when it runs again and, as a service that runs once, has no healthcheck ([Compose spec rules](#compose-spec-rules)). SearXNG is pinned (the guide runs `latest`), mounts [searxng-settings.yml](./compose/n8n/assistant/searxng-settings.yml), which turns on the JSON format the Assistant asks for, and always runs with the Assistant. No host ports and no traefik route.
* `sandbox-runner-1` is Docker in Docker: `privileged: true` and without `no-new-privileges`. n8n documents this bundled sandbox as for development and testing only, since code that escapes it reaches the host; a production instance uses the sandbox service on Kubernetes or a managed sandbox, both configured in the Assistant settings of n8n and out of scope here, like Brave Search.
* By hand, from `compose/n8n/`: `docker compose -f assistant/docker-compose.yml up -d`, then `N8N_ASSISTANT=true docker compose -f docker-compose.<variant>.yml up` with the model in `.env`.

### `compose/models/` engines and the model catalogue

`AI_ENGINE` picks the engine (`ollama` or `vllm`), `AI_RUNTIME` the compose profile and `AI_MODELS` the models that start with the stack (mapped by `modelProjects()` in [tilt.ts](./packages/cli/src/commands/tilt.ts)):

| File | Role |
| --- | --- |
| [models.json](./compose/models/models.json) | the catalogue: one `models` list with one entry per model, validated by the CLI with [models.ts](./packages/cli/src/schemas/models.ts) and in editors with [models.schema.json](./compose/models/models.schema.json). An entry has an `id` (the `AI_MODELS` value; a plain DNS label of at most 58 characters, since the docker names of the model are `<engine>-<id>` and must fit a 63-character label), a `label` shown by `models select`, and a block per engine that serves it (`ollama`, `vllm`; at least one) with the engine's `model` name (an ollama tag such as `qwen3.5:0.8b`, a Hugging Face id such as `Qwen/Qwen3.5-0.8B`), vllm `args`, a `memory` shown by `models select` (an estimate in GB stored as a number; the CLI prints it as `~6 GB RAM`, or VRAM on a gpu runtime), an optional `note` shown after the memory, and an optional `runtimes` list when that engine runs the model only on some hardware |
| [models.cloud.json](./compose/models/models.cloud.json) | the cloud models `config N8N_ASSISTANT` offers for [the n8n Assistant](#the-n8n-assistant-n8n_assistant), validated by the CLI with [assistant.ts](./packages/cli/src/schemas/assistant.ts) and in editors with [models.cloud.schema.json](./compose/models/models.cloud.schema.json): a list of `providers`, each with an `id` (what n8n reads before the first slash of `N8N_INSTANCE_AI_MODEL`, such as `anthropic`), a `label` and its `models`, each with an `id` (the name at the provider, which may nest a vendor as `deepseek/deepseek-v4-pro` does on openrouter), a `label` and an optional `note`. The first model of the first provider is the default of the n8n compose file. It is no part of the engine catalogue: nothing here is served locally and `tilt resources` does not read it |
| `<engine>/docker-compose.yml` | the engine: one service per `AI_RUNTIME` named `<engine>-<runtime>` (`ollama-cpu-arm64`, `vllm-gpu-nvidia`, …), each in the compose profile of the same name, all sharing an `x-<engine>` anchor. No model name lives in a compose file, `tilt resources` passes them in from the catalogue (the one exception is the cloud default of the Assistant in the n8n compose file) |

The engines deploy differently, and the Tilt plan mirrors that:

| Engine | Containers | Tilt resources | Reachable at |
| --- | --- | --- | --- |
| `ollama` | one server pulls every model of `AI_MODELS` on start; pulled models stay in the volume and n8n can pull more through the API | `ollama`, auto-started when `AI_MODELS` lists a model, otherwise registered for a manual start | `http://ollama:11434` on `n8n-starter-private` |
| `vllm` | one container per model of `AI_MODELS`, since a vLLM process serves one model | `vllm-<id>` per listed model, all auto-started; nothing is registered for the other catalogue entries | `http://vllm-<id>:8000/v1` on `n8n-starter-private`, the id being the `id` of the catalogue entry (`vllm-qwen3-5-0-8b`) |

`AI_GATEWAY` puts a gateway in front of the engine, so n8n needs one credential instead of one per vllm container. It is empty by default, which runs none; `litellm` starts [LiteLLM](./compose/models/litellm/README.md) with its own PostgreSQL (`litellm-db`), next to either engine:

| Gateway | Containers | Tilt resources | Reachable at |
| --- | --- | --- | --- |
| `litellm` | the proxy and its database, which keeps the UI state and the models added there | `litellm-db` and `litellm`, registered always and enabled only by `AI_GATEWAY=litellm` | `http://litellm:4000/v1` on `n8n-starter-private` and `litellm.<DOMAIN>` through traefik (UI and API), behind `LITELLM_MASTER_KEY` of `compose/models/litellm/.env`; the model name is the `id` of the catalogue entry |

Rules of the gateway:

* The gateway serves exactly the models of `AI_MODELS`, each under its catalogue `id`, whichever engine runs it: an OpenAI compatible client sends `model: qwen3-5-0-8b` to the one endpoint. `config AI_GATEWAY` and `models select` print that endpoint.
* The model list reaches the proxy like the models reach an engine, through an inline override that `tilt resources` builds from the catalogue: the compose file declares the config `litellm-config` (mounted at `/app/config.yaml`, an empty `model_list` by hand) and the override replaces its `content` with one entry per id: `ollama_chat/<tag>` at `http://ollama:11434`, or `hosted_vllm/<Hugging Face id>` at `http://vllm-<id>:8000/v1` with `api_key: os.environ/VLLM_API_KEY` ([vLLM](https://docs.litellm.ai/docs/providers/vllm) and [Ollama](https://docs.litellm.ai/docs/providers/ollama) in the LiteLLM docs). The content is JSON, which the proxy reads as YAML, so the CLI needs no YAML writer. Inline configs need Docker Compose 2.23.1, which the required 2.24 covers.
* `VLLM_API_KEY` in `compose/models/litellm/.env` is a link to the key of `compose/models/vllm/.env` (see [Secrets](#secrets)), so the proxy authenticates against the vllm containers without a second copy to maintain.
* A changed list recreates the proxy, nothing else does. Compose and Tilt decide by the service definition, which the content of a config is not part of (`docker compose config --hash litellm` is the same for every list), and Compose writes an inline config into the container only when it is created. So the override also labels the `litellm` service with `n8n-starter.config-hash=<hash of the content>`: `models select`, an `AI_ENGINE` change or an edited model name in the catalogue changes the label and Tilt recreates the container on its reload, while a `DOMAIN` or `N8N_VARIANT` change leaves it running. `litellm-db` is never touched.
* Models added in the LiteLLM UI are stored in its database (`STORE_MODEL_IN_DB`) and served beside the generated list; the generated entries follow `AI_MODELS` on every Tilt reload.
* The gateway has no start-order dependency on the model servers: it proxies per request, and a model server can take minutes to turn healthy.
* Adding a gateway means a directory under `compose/models/`, its name in `AI_GATEWAYS` ([config.ts](./packages/cli/src/schemas/config.ts)) and in the `Options:` comment of the root `.env.template`, its endpoint in `GATEWAYS` ([models.ts](./packages/cli/src/utils/models.ts)) and its project in `gatewayProjects()` ([tilt.ts](./packages/cli/src/commands/tilt.ts)).

Entries, the same ids in both lists:

| Id | Model | Why |
| --- | --- | --- |
| `qwen3-5-0-8b` | Qwen3.5 0.8B (text + vision, tools, thinking opt-in per request) | lightweight default on both engines for smoke tests; 1.6 GB bf16 weights on vLLM, about 10 GB on CPU with the runtime overhead, the default KV cache and the vision processors (7.5 GB text only) |
| `qwen3-5-2b` | Qwen3.5 2B (text + vision, tools, thinking opt-in per request) | the middle step, still on every runtime of both engines; 4.5 GB bf16 weights on vLLM, about 12 GB on CPU with the runtime overhead, the default KV cache and the vision processors, which the Docker VM needs free beside the rest of the stack |
| `qwen3-5-4b` | Qwen3.5 4B (text + vision, tools, thinking opt-in per request) | successor of the upstream starter kit's `llama3.2`; 3.3 GB on ollama, 9.3 GB bf16 weights on vLLM, an estimated 17 GB on CPU with the runtime overhead, the default KV cache and the vision processors (not measured, the development VM is too small), so it wants a Docker VM with that much free |

vLLM on CPU loads bf16 weights (about 2.3 GB per billion parameters) and allocates the KV cache of `VLLM_CPU_KVCACHE_SPACE` on top, while ollama serves 4-bit quantizations that fit a laptop. Every entry runs on every runtime of both engines: the `memory` estimate `models select` shows is the only guard, and `runtimes` is reserved for a model an engine cannot run on some hardware, not for what a given machine can afford.

Rules of the catalogue:

* Per container exactly one service runs: the one in the profile named after `AI_RUNTIME` (`COMPOSE_PROFILES=$AI_RUNTIME` by hand, `profiles=[AI_RUNTIME]` in Tilt). `cpu-arm64` also covers Apple silicon Macs, where Docker cannot use the GPU, and is the default because Apple silicon MacBooks are the usual developer machine; `cpu-x86-64` runs there too, but through emulation. The default is always the first entry wherever the runtimes are listed (template, CLI schema, `config` prompt). The CLI detects the platform ([platform.ts](./packages/cli/src/utils/platform.ts)) from one `docker info` line (the daemon's `Architecture`, its `MemTotal`, which is the Docker VM memory on Docker Desktop and OrbStack, its `NCPU` and its `Runtimes`) plus the host (`os.arch()`, `os.platform()`, `os.totalmem()`, the ROCm device `/dev/kfd` on Linux) and maps it to a runtime: the `nvidia` docker runtime (registered by the NVIDIA Container Toolkit, shipped by Docker Desktop on Windows) is `gpu-nvidia`, `/dev/kfd` on a Linux host is `gpu-amd`, otherwise the daemon's architecture (the host's when docker is down) picks `cpu-arm64` or `cpu-x86-64`; macOS never passes a GPU to Docker. `setup` writes that runtime into a root `.env` it creates, `config AI_RUNTIME` marks it with a green `(detected)` on its row of the prompt, `verify` and `config` warn when `AI_RUNTIME` differs from it (a warning, never a failure: emulation and a CPU runtime on a GPU machine are legitimate), and `models select` prints the detected line and points out an estimate above the docker memory on the CPU runtimes.
* The models reach the compose file through an inline override of the runtime service that `tilt resources` ([tilt.ts](./packages/cli/src/commands/tilt.ts)) builds from the catalogue and the Tiltfile passes as `docker_compose([<engine>/docker-compose.yml, encode_yaml(override)])`: the container variable `MODELS` (comma separated tags) for ollama; `MODEL`, `MODEL_ARGS` and the `container_name` for each vllm model, which runs as its own compose project. Tilt resource, compose project, container and hostname of a vllm model all use `vllm-<id>` with the `id` of the catalogue entry, which is a plain DNS label precisely because compose project names and hostnames require one; `models select` prints the endpoint of every selected model. Environment variables cannot do this: `os.putenv` is global to the Tilt process, so every project would see the last value.
* Container variable names are neutral on purpose: `OLLAMA_MODELS` is Ollama's own setting for its model directory, and vLLM warns about every unknown `VLLM_*` variable. The engine-scoped names exist for running an engine by hand, as compose interpolation with defaults: `OLLAMA_PULL_MODELS=qwen3.5:0.8b,qwen3.5:4b docker compose --profile cpu-arm64 up` from `compose/models/ollama/`, and `VLLM_MODEL=Qwen/Qwen3.5-0.8B VLLM_MODEL_ARGS=… VLLM_MODEL_ID=qwen3-5-0-8b docker compose -p vllm-qwen3-5-0-8b --profile cpu-arm64 up`, `VLLM_EXTRA_ARGS` being the third one from `compose/models/vllm/` (the container `vllm-<VLLM_MODEL_ID>` is the hostname, so pass the id already normalized). vLLM stops with a message when `MODEL` is empty at container start; a compose-time `${VAR:?}` is impossible because Tilt sets the container variables, not the interpolation ones. This is the one exception to the `${VAR:?}` rule below.
* Download and inference happen in one service: ollama pulls the models in the background of `ollama serve` (which stays PID 1), vLLM downloads from Hugging Face on start (`HF_TOKEN` is only needed for gated models) and requires the `VLLM_API_KEY` of `compose/models/vllm/.env` as bearer token on its `/v1` endpoints (the name is vLLM's own variable, so it is passed through unchanged; `/health` stays open for the healthcheck). The healthcheck only turns healthy once every model is available, so `start_period` is generous. Changing `AI_MODELS` restarts the ollama server with the new list and adds or removes vllm containers.
* Runtime-specific `vllm serve` flags live in `command` of the compose file, model-specific ones in the catalogue `args` (context length, tool-call parser), so an entry never repeats runtime settings, and machine-specific ones in `VLLM_EXTRA_ARGS` of `compose/models/vllm/.env` (container variable `EXTRA_ARGS`), which the entrypoint appends last so a machine overrides the runtime and the model; Tilt watches that file and redeploys the vllm containers on a change. The Qwen3.5 entries carry no `--reasoning-parser`: their chat template runs non-thinking unless a request sets `enable_thinking`, and vLLM's `qwen3` parser files everything before a `</think>` as reasoning, so a non-thinking answer came back with `content: null` and n8n showed an empty output. Without the parser the answer is the `content`, and a client that opts into thinking gets the `</think>` text inline. On CPU the compose file sets `--dtype=bfloat16`, the container variable `VLLM_CPU_KVCACHE_SPACE` (an absolute KV cache size in GiB, default `2`, the knob of `compose/models/vllm/.env`; the gpu runtimes ignore it) and `--skip-mm-profiling`: vLLM profiles the vision encoder of a multimodal model with a maximum-size image at start, which on CPU takes longer than the 15 minute `start_period` (over 20 minutes for Qwen3.5 0.8B against about a minute without), so the CPU runtimes skip that profiling and keep vision; the activations of an image request then come on top of weights and KV cache and are not reserved at start, the price of the fast start. Keeping vision costs about 2.5 GB at start regardless of the machine (measured with Qwen3.5 0.8B: 10 GB against 7.5 GB text only, most of it the image processors in the API server, about 1 GB of it the multimodal processor cache that `--mm-processor-cache-gb=0` removes), and the `memory` of the catalogue includes it; a machine that wants text only sets `VLLM_EXTRA_ARGS='--limit-mm-per-prompt={"image":0,"video":0}'` (7.5 GB instead of 10 GB for the 0.8B), `--mm-processor-cache-gb=0` there trims about 1 GB while keeping vision, and an entry that should serve text only everywhere puts the limit flag in its `args`. Text-only models accept the flag unchanged. The catalogue caps every entry at `--max-model-len=32768`, well below the 262144 of the Qwen3.5 models: with an absolute KV cache the cap does not drive memory (2 GiB hold several such sequences), it bounds the prefill time of one request on CPU. The KV cache is absolute on purpose: by default vLLM reserves a share of the memory it sees (`--gpu-memory-utilization`, `0.92`, which on CPU is the whole Docker VM) and refuses to start when that share is not free, and the share a model needs changes with the VM size, so no fixed value suits every machine; with an explicit KV cache vLLM skips that check and a container needs its weights, the runtime overhead and the cache, whatever the VM size. vLLM maps the variable to `--kv-cache-memory-bytes`, which `v0.31.0` only accepts as a byte count, hence the GiB variable; switch to the flag when a version drops the variable.
* Model weights are bind-mounted under `.volumes/models/<engine>/` like all other runtime data; all vllm containers share one Hugging Face cache. No host ports and no traefik route: the model APIs are only reachable on `n8n-starter-private`, vllm additionally behind its `VLLM_API_KEY`. The gateway is the one routed way in, behind its own key.
* Adding a model means adding one catalogue entry with a block per engine that serves it. `models select` lists every entry and disables those the chosen runtime cannot run, and `tilt resources` (so the Tiltfile) fails on an `AI_MODELS` id the engine does not serve on `AI_RUNTIME`, which is also what happens to a root `.env` that still lists an id the catalogue renamed: `pnpm run models select` rewrites it. The default `AI_MODELS=` starts no model.

### Compose spec rules

* Image tags are pinned to an exact version, either literally or through an `.env` variable such as `N8N_VERSION`.
* Services only join the two external networks described below; a compose file never creates networks of its own.
* A service is exposed through traefik with the label `traefik.enable=true`. Host ports are only published for tools that need direct access (e.g. postgres `5432`, redis `6379`); traefik binds `80` on `127.0.0.1` only.
* Every service that keeps running has a `healthcheck` in its compose file: one inherited through `extends` or an anchor counts, the `HEALTHCHECK` of an image does not, and neither does a disabled one. The one exception is a service that runs once and exits, which another service of the file waits for with `depends_on: condition: service_completed_successfully` (`sandbox-certs`): it has none, because Docker reports a stopped container that has a healthcheck as `unhealthy`, whatever its exit code, and Tilt shows that as a failed resource. The probe runs a tool the pinned image ships: `wget` or `curl` against the service's health endpoint, the service's own CLI where the image holds nothing else (`/garage status`), or an HTTP request over bash's `/dev/tcp` where it has neither (`qdrant`); the task runner sidecars probe the health check server of their launcher (`/healthz` on port `5680`). Dependants use `depends_on: condition: service_healthy` where start order matters.
* Containers run with `security_opt: no-new-privileges=true` where the image allows it, and the docker socket is never mounted into traefik directly – only into the read-only `docker-socket-proxy`.
* Shared config is factored into YAML anchors (`x-*` blocks) within a file. Across files only `.env` variables and the `compose/n8n` variant cascade (`extends`) are shared.
* Every interpolated variable is either required, `${VAR:?}`, or optional with its default in the compose file, `${VAR:-default}` (e.g. `N8N_LOG_LEVEL`, `VOLUMES_PATH`, `DOMAIN`). Required is reserved for secrets and pinned versions: the `.env.template` next to the file lists a pinned version with its value and a secret as an empty key (`N8N_ENCRYPTION_KEY=`) that `setup` fills from the `.env.json` beside it (see [Secrets](#secrets)), so a copied but unfilled `.env` stops the service with a clear error instead of starting it with a known value. Optional knobs a developer may change (`N8N_PROTOCOL`, `VLLM_CPU_KVCACHE_SPACE`, `VLLM_EXTRA_ARGS`, `TZ`, …) appear in that template commented out with their default (`# N8N_PROTOCOL=http`), so the default lives in exactly one place; everything else stays out of the template, and a service with nothing to list has no template at all. A template with both kinds is grouped into sections, required first: a one-line header `# required` or `# optional` (with `, defaults live in ./docker-compose.yml` on the optional one) and a blank line before each; the n8n template adds the variant scope to the header (`all variants`, `build, community and enterprise variants`, `community and enterprise variants`, `enterprise variant`, widest first), and a key that is both required and variant-specific (`N8N_LICENSE_ACTIVATION_KEY`) is placed by its requirement. Bare `${VAR}`, `$VAR` and `environment: - VAR` entries are never used: they resolve to empty without an error. Literal credentials and machine-specific paths do not belong in a compose file either.
* Comments in compose and `.env.template` files stay short and point to where the reasoning lives instead of repeating it: this document holds the strategy and its rules, compose mechanics are documented by Docker, and n8n settings at [docs.n8n.io](https://docs.n8n.io), which coding agents reach through the `n8n-docs` MCP server registered in [.mcp.json](./.mcp.json) and [.vscode/mcp.json](./.vscode/mcp.json).
* `pnpm run lint` must pass: dclint with `--max-warnings 0`, so warning-level rules (key order, project name, quotes) fail the gate like errors (`no-version-field` is the only rule switched off, the `version:` key is obsolete in the compose spec), followed by `lint:env`, a grep that fails on any bare `${VAR}` or `$VAR` in a compose file, and `lint:healthcheck`, which renders every compose file with `docker compose config --no-interpolate` (all profiles, no `.env` and no daemon needed) and fails with the file and the service names when a service has no healthcheck, unless another service of the file waits for it with `service_completed_successfully`; it needs `docker compose` and `jq`.

## Docker networks

All compose specs use `n8n-starter-public` and `n8n-starter-private` docker networks as a minimal isolation strategy.

* `n8n-starter-public` holds traefik and every container it routes to (compose label `traefik.enable=true`).
* `n8n-starter-private` holds everything traefik does not route to, e.g. databases and storage.
* A routed service that also needs a backend joins both (n8n, n8n-webhook, pgadmin, redis-insight, litellm). Traefik itself joins both so it can reach `docker-socket-proxy` on the private side.

| Network | Members |
| --- | --- |
| `n8n-starter-public` only | garage, garage-webui |
| `n8n-starter-private` only | docker-socket-proxy, postgres, redis, n8n-runner, n8n-worker, n8n-worker-runner, sandbox-api, sandbox-runner-1, searxng, qdrant, ollama, vllm, litellm-db |
| both | traefik, n8n, n8n-webhook, pgadmin, redisinsight, litellm |

The one-shot `sandbox-certs` joins none (`network_mode: none`): it only writes files. Both networks are declared as `external` in the compose specs and are created by `pnpm run setup`, so run it once before `pnpm run dev`. Traefik's docker provider is pinned to `network: n8n-starter-public` so it always dials routed containers over the public network, even when they sit on both.

## Routing

Traefik discovers services through labels via `docker-socket-proxy` (`exposedByDefault: false`, so only `traefik.enable=true` services are routed). The default rule routes every exposed service at `<compose service name>.<DOMAIN>`, e.g. `pgadmin.n8n.localhost`; only n8n itself overrides this and is served at the bare `DOMAIN`, and in queue mode the webhook processor is served at `hooks.<DOMAIN>`: main sets `N8N_WEBHOOK_URL` to that host, its router `n8n-webhook` takes every path of the host and a second router on main (`n8n-hooks-test`, longer rule so it wins without a priority) takes the test prefixes `/webhook-test/`, `/form-test/` and `/mcp-test/` back, because n8n derives test and production URLs from the one `N8N_WEBHOOK_URL` ([Configure webhook URLs with reverse proxy](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/configure-webhook-urls-with-reverse-proxy)). Services with several ports (garage) declare their own routers; those of the S3 API and the web endpoint also match one bucket label below `s3.<DOMAIN>` and `web.<DOMAIN>` (`my-bucket.s3.<DOMAIN>`, the `root_domain` of the garage config for that `DOMAIN`), the vhost-style addressing of garage. The model servers are not routed at all, only the optional gateway in front of them is, at `litellm.<DOMAIN>` ([engines and catalogue](#composemodels-engines-and-the-model-catalogue)).

The stack runs plain HTTP only ([traefik.yml](./compose/proxy/traefik/traefik.yml): one `web` entrypoint on `80`, no TLS, no HSTS headers); HTTPS is not supported yet.

`DOMAIN` is one of two values, and `n8n.localhost` is the default for these reasons:

| | `n8n.localhost` (default) | `n8n.local` |
| --- | --- | --- |
| Name resolution | Chrome and Firefox resolve `*.localhost` to the loopback themselves on every OS, as do systemd-resolved and current macOS and curl releases; older command-line tools need a hosts file entry | none without setup, and a failed lookup waits for the mDNS timeout: `.local` belongs to mDNS ([RFC 6762](https://www.rfc-editor.org/rfc/rfc6762)), so every hostname needs a hosts file entry (or an mDNS publisher on the host, which the stack does not ship). Linux [nss-mdns](https://github.com/avahi/nss-mdns) refuses names with more than two labels such as `traefik.n8n.local` by default, and a network whose Active Directory domain ends in `.local` conflicts with it |
| Reach from the local network | no, the loopback by definition | not by the name alone: traefik binds `127.0.0.1` and the names would have to be published to the other devices |
| Browser features over plain HTTP | `http://*.localhost` is a [secure context](https://www.w3.org/TR/secure-contexts/#is-origin-trustworthy) | `http://n8n.local` is not, so it depends on HTTPS |
| A self-signed certificate later | `*.n8n.localhost` plus `n8n.localhost` | `*.n8n.local` plus `n8n.local`, equally valid: both wildcards sit below a second label, which `*.localhost` and `*.local` would not; every other device would need the root certificate installed |

`n8n.local` is therefore the shorter name and fits the planned certificates, but only serves the local network once the names are published, traefik listens beyond the loopback and HTTPS exists. Until then it needs one hosts file line with every hostname of the stack, and `config DOMAIN n8n.local` warns about it.

n8n runs with `N8N_PROXY_HOPS=1` because Traefik is the only proxy in front of it, so Express trusts one hop of `X-Forwarded-*` headers when it determines client IPs (rate limiting, Webhook node IP whitelists). Raise the value in `compose/n8n/.env` by one for every additional proxy or load balancer placed in front of Traefik.

## Configuration

The root `.env`, generated from [.env.template](./.env.template), steers the whole environment and is edited one key at a time with `pnpm run config` (asks which key, then prompts it), `pnpm run config <KEY>` (prompts that key) or `pnpm run config <KEY> <value>` (writes without a prompt, for scripts and agents); `AI_MODELS` has its own command, `pnpm run models select [ids]`, because its prompt is a multi-select over the catalogue, and `pnpm run config AI_MODELS [ids]` runs that command; `N8N_ASSISTANT` is the one key with a second value, `pnpm run config N8N_ASSISTANT true [model]`, because switching the Assistant on also picks its model ([the n8n Assistant](#the-n8n-assistant-n8n_assistant)):

```bash
# Which variant of n8n to run in ./compose/n8n
# Options: dev, build, community or enterprise
N8N_VARIANT=dev
# The n8n Assistant with its sandbox and web search in ./compose/n8n/assistant
# Options: false or true, `pnpm run config N8N_ASSISTANT` also picks its model: a cloud provider model or one of AI_MODELS
N8N_ASSISTANT=false
# The hardware supported ai runtime
# Options: cpu-arm64, cpu-x86-64, gpu-nvidia or gpu-amd
AI_RUNTIME=cpu-arm64
# The engine serving the AI models in ./compose/models
# Options: ollama or vllm
AI_ENGINE=ollama
# The gateway in front of the AI models in ./compose/models, one OpenAI compatible endpoint and key for every model of AI_MODELS
# Options: empty for none, or litellm
AI_GATEWAY=
# The models of ./compose/models/models.json that start with the stack, comma separated ids such as qwen3-5-0-8b,qwen3-5-2b
# ollama pulls them into one server, vllm runs one container per model, pick them with `pnpm run models select`
AI_MODELS=
# The domain to run the docker compose services
# Options: n8n.localhost or n8n.local, which resolves only with a hosts file entry per hostname (see ./SPEC.md)
DOMAIN=n8n.localhost
```

`AI_GATEWAY` and `N8N_ASSISTANT` are the keys that may be absent: a root `.env` written before they existed reads as an empty gateway and `N8N_ASSISTANT=false`, which runs neither, and `pnpm run config AI_GATEWAY litellm` or `pnpm run config N8N_ASSISTANT true` appends the key. Everything else (image versions, credentials, license keys, the model of the Assistant) lives in the per-service `.env` next to the compose file it belongs to. The rules:

* `.env` and `.env.secrets` files are never committed; only the `.env.template` files and the `.env.json` manifests are. `.gitignore` covers `.env`, `.env.secrets`, `.volumes` and `dist`.
* `setup` only ever creates missing `.env` files and fills empty secrets; it never overwrites a value a human or an earlier run wrote, so local edits survive re-runs (the exceptions are derived state: a link always follows its source and a derived value such as the owner password hash its input, see [Secrets](#secrets)). The one value it sets in a file it created itself is `AI_RUNTIME` of a new root `.env`, replaced by the detected runtime in the same run; an existing root `.env` only gets a warning when its runtime does not fit.
* `reset` deletes all generated `.env` and `.env.secrets` files after confirmation and keeps the templates and manifests.
* Editing a per-service `.env` while Tilt runs reloads the Tiltfile (see [Developer experience with Tilt](#developer-experience-with-tilt)): `verify` runs again, so a secret edited out of step with its link fails the gate at once, and Tilt recreates exactly the services whose rendered configuration changed, a version bump or a knob included, and leaves the rest running. A changed `N8N_ENCRYPTION_KEY` takes effect the same way and makes the stored credentials unreadable. A `.env.secrets` is not watched: `secrets set` rewrites the hash in the `.env` together with the password, and a hand edit takes effect with the next `pnpm run setup`.
* `VOLUMES_PATH` is optional and defaults to the repo's `.volumes/` from every compose file. It is the single knob to move all runtime data elsewhere, e.g. `VOLUMES_PATH=/Volumes/ext/n8n pnpm run dev`. An exported variable wins over a per-service `.env`, and because every compose project inherits it, it must always point at a `.volumes`-style root, not at a service folder.
* Secret keys are empty in the templates and filled by `setup` as the `.env.json` next to the template declares (see [Secrets](#secrets)).
* The instance owner of n8n is managed by env in every variant ([manage settings using environment variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/manage-settings-using-environment-variables#instance-owner), from n8n 2.17.0): `x-n8n-env-owner` of the base file sets `N8N_INSTANCE_OWNER_MANAGED_BY_ENV` (`true`), `N8N_INSTANCE_OWNER_EMAIL` (`owner@example.com`), `N8N_INSTANCE_OWNER_FIRST_NAME` (`Instance`) and `N8N_INSTANCE_OWNER_LAST_NAME` (`Owner`) as knobs with generic defaults, and the required `N8N_INSTANCE_OWNER_PASSWORD_HASH`, which must be a bcrypt hash: `setup` derives it from `N8N_INSTANCE_OWNER_PASSWORD` in `compose/n8n/.env.secrets`. n8n overwrites the owner with these values on every start, makes the matching UI controls read-only and rejects API writes, so nobody creates the owner in the browser: `pnpm run secrets read n8n` prints the login, the email changes in `compose/n8n/.env` ([change instance owner email](https://docs.n8n.io/deploy/host-n8n/configure-n8n/change-instance-owner-email)) and the password with `pnpm run secrets set N8N_INSTANCE_OWNER_PASSWORD`. `N8N_INSTANCE_OWNER_MANAGED_BY_ENV=false` gives the UI its write access back and keeps the values last applied. The worker and the webhook processor inherit the variables through `extends`; only the `start` command applies them ([start.ts](https://github.com/n8n-io/n8n/blob/master/packages/cli/src/commands/start.ts) of n8n, not stated in its docs).
* In `compose/n8n/.env` ([template](./compose/n8n/.env.template)), the sections named after a variant in their header list the keys only that variant uses: the postgres keys, the runner token `N8N_RUNNERS_AUTH_TOKEN` and the Python allowlists are only used from the `build` variant up (`dev` runs on SQLite with the internal runner), the license keys only by the `enterprise` variant, and `OFFLOAD_MANUAL_EXECUTIONS_TO_WORKERS` / `QUEUE_WORKER_CONCURRENCY` / `N8N_WEBHOOK_REPLICAS` / `N8N_DISABLE_PRODUCTION_MAIN_PROCESS` only in queue mode (`community`, `enterprise`).
* `DOMAIN` is `n8n.localhost` or `n8n.local` and nothing else, because no other domain strategy is supported ([Routing](#routing)): the CLI offers the two as a select and rejects any other value, in `config DOMAIN <value>` and in a root `.env` edited by hand, where it stops the Tilt plan. It defaults to `n8n.localhost` in every compose file that uses it (traefik, n8n, garage) and in the root [.env.template](./.env.template). Compose itself cannot restrict a value, so `DOMAIN=… docker compose` by hand takes any hostname, unsupported. Tilt exports the root `.env`, and a shell variable wins over the `.env` next to a compose file, which wins over the compose default, so the root `.env` steers every project while `docker compose` by hand needs nothing. `N8N_ASSISTANT` reaches the n8n compose files the same way, with `false` as their default.
* Tilt and the CLI are conveniences, never requirements. Any service runs with plain `docker compose up` from its directory once the two docker networks exist (`docker network create n8n-starter-public` and `n8n-starter-private`), its `.env.template` is copied to `.env` with the empty secret keys filled by hand (a value that holds `$`, the bcrypt hash of the n8n owner password for one, in single quotes so compose does not interpolate it) and the services it talks to are up; `pnpm run setup` does the first two for every service at once.

### Secrets

A `.env.json` next to a `.env.template` declares which of its keys are secrets and how the CLI fills them; [compose/.env.schema.json](./compose/.env.schema.json) is the editor schema and [secrets.ts](./packages/cli/src/schemas/secrets.ts) the validated shape. A service directory so holds up to four env files: the committed `.env.template` and `.env.json`, the `.env` compose reads and, for the secrets no container reads, a `.env.secrets` beside it (both gitignored, the second created by the CLI for its owner only). Manifests exist for `compose/n8n`, `compose/n8n/assistant`, `compose/storage/postgres`, `compose/storage/pgadmin`, `compose/models/litellm` and `compose/models/vllm`; the root `.env` never holds a secret because the Tiltfile prints it. Each entry has a `source`:

* `generate`: a value `setup` writes, as its `generator` says. `random`, the default, is written once (`bytes` 32, `encoding` `hex` or `base64url`, an optional `prefix` such as litellm's `sk-`). `bcrypt` is the hash of its `input`, a random `generate` key of the same manifest (`rounds` 10 by default, the cost n8n hashes with): a derived value that follows its input the way a link follows its source. Another way to generate is one more member of the `generator` union in [secrets.ts](./packages/cli/src/schemas/secrets.ts) and one case in [generators.ts](./packages/cli/src/utils/generators.ts). `file` names the file that holds the value: `.env`, the default, or `.env.secrets` for a secret no container reads, as `N8N_INSTANCE_OWNER_PASSWORD`, whose hash `N8N_INSTANCE_OWNER_PASSWORD_HASH` is what n8n gets. `rotation` says what changing it later costs: `free` (a restart), `manual` (the service keeps its own copy: a postgres password only applies when the data directory is created) or `never` (`N8N_ENCRYPTION_KEY` and `LITELLM_SALT_KEY` encrypt stored data; n8n states that the instance key [never changes](https://docs.n8n.io/deploy/host-n8n/configure-n8n/security/rotate-encryption-keys)). `reset` warns about the `manual` and `never` keys that are set, `secrets set` warns before replacing a `never` key.
* `prompt`: a value only a human knows, set with `secrets set`. With `required` (root `.env` values, every listed key must match) `verify` fails without it, as `N8N_LICENSE_ACTIVATION_KEY` for `N8N_VARIANT=enterprise`; without `required` it is optional (`HF_TOKEN`) and stays commented out in the template.
* `link`: a copy of a `generate` or `prompt` secret of another directory (`from` relative to the manifest, plus `key`), as `DB_POSTGRESDB_PASSWORD` of postgres's `POSTGRES_PASSWORD` and litellm's `VLLM_API_KEY` of vllm's. A link never points at a link. With `required` (root `.env` values, as on a `prompt`) it is a conditional link, for a key the consumer needs only under those values: n8n's `N8N_SANDBOX_SERVICE_API_KEY` of the assistant's `SANDBOX_API_KEYS`, required for `N8N_ASSISTANT=true`. `setup` fills it like every link, but the service must run without it.

A `generate` or `prompt` entry may name `related` keys: keys of the same template that are no secrets but belong to this one, as `N8N_INSTANCE_OWNER_EMAIL` to the owner password. `secrets read` prints them with the secret.

The rules:

* A secret key is live and empty in its template (`N8N_ENCRYPTION_KEY=`) and `${KEY:?}` in the compose file, so an unfilled `.env` stops the service instead of starting it with a known value; an optional `prompt` key and a conditional link are commented out and `${KEY:-}` (`setup` appends the link to the `.env`), and a `.env.secrets` key is in neither the template nor a compose file. A `related` key is a key of the template: live with a value, or a commented knob. A test over the repository checks every manifest against its template, its compose files and the editor schema, that every required `PASSWORD`, `SECRET`, `_KEY` or `TOKEN` interpolation of the catalogue is declared, and that the commented default of a `related` knob is the default of the compose file.
* A value is unfilled while it is absent, empty or still equal to the template value. `setup` generates every unfilled random key once and never touches a filled one; on every run it then sets every derived value to what its input gives and every link to its source (both are derived state, so this stays idempotent and repairs them after the input or the source was set by hand; a hash is rewritten only while it is empty or no longer fits its input, so its salt stays between runs). A hash pasted into a `.env` by hand is therefore replaced, and a deleted `.env.secrets` means a new password: set the password with `secrets set` instead. It never prompts, a required `prompt` key is a warning pointing at `secrets set`.
* `verify` reports an unfilled generated or linked key (`Missing secret`), a link that differs from its source, a derived value that does not match its input and a required `prompt` key that is unset under the current root `.env`, so the Tiltfile gate refuses `enterprise` without a license key. An optional unset key is information only, and so is an unfilled conditional link while the root `.env` does not meet its condition; once it does, it is missing like any other link, with the condition named. `config` warns the same way right after a variant, engine or runtime change.
* `secrets read [filter]` prints the declared secrets as `KEY=value` lines grouped by the file that holds them on stdout and nothing else (`filter` is a case-insensitive part of a directory or key; a filter that is the directory of a manifest keeps that directory alone, so `compose/n8n` does not list the manifest nested in `compose/n8n/assistant`; an exact key prints only its value, one line per manifest that declares it, so it can be piped). The `related` keys of a secret are printed above it, with the value of the `.env`, else the live value or the commented default of the template, so the n8n block ends with the email and the password of the owner login. A derived value is left out unless it is named: a hash is of no use to a reader. A missing `.env` or `.env.secrets` fails naming the file.
* `secrets set KEY [value]` writes one `generate` or `prompt` key (a masked prompt without `value`), then what is derived from it and its links; a link or a derived key is refused with a pointer to the key it follows, and a hash that still fits is left alone. A value is written in single quotes when compose or node would read part of it as syntax (`$`, `#`, a space, a quote) and refused when it holds a single quote, a backslash or a line break, which no quoting stores the same way for both.
* Out of scope for now: the literal tokens in `compose/storage/garage` (enterprise wiring), docker secrets and n8n's `_FILE` variables (vllm and pgadmin have no file variant), and rotation (`secrets rotate` is on the roadmap; the `rotation` field already carries what it needs).

## Developer experience with Tilt

`pnpm run dev` runs `tilt up` followed by `tilt down`, so leaving Tilt with Ctrl+C also stops and removes every container it started (Tilt alone would leave Docker Compose services running). `tilt down` re-evaluates the Tiltfile, keeps the docker networks, `.env` files and volumes, and only removes containers; pressing Ctrl+C a second time aborts the teardown, in which case run `pnpm exec tilt down` by hand. The [Tiltfile](./Tiltfile):

1. Loads the root `.env` via the `dotenv` extension, so every compose project it starts inherits `DOMAIN` and the n8n project `N8N_ASSISTANT`.
2. Runs `n8n-starter tilt resources --log-level error` ([tilt.ts](./packages/cli/src/commands/tilt.ts)) through `local()` and `decode_json`s the plan: the validated root configuration (printed as the banner) and every compose project to register with its files, project name, profiles, inline override, `secrets` (its directory, when a `.env.json` sits beside its compose file) and resources (name, labels, `resource_deps`, `links`, `infer_links`, `auto_init`, `enabled`), validated by [tilt.ts](./packages/cli/src/schemas/tilt.ts) (unique names, dependencies that exist and are enabled when the dependant is). An invalid `.env` key, an `AI_MODELS` id the engine does not serve on the runtime or, with `N8N_ASSISTANT=true`, a model in `compose/n8n/.env` that points at a model server which no longer serves it ([the n8n Assistant](#the-n8n-assistant-n8n_assistant)) fails the command with the reason, and with it the Tiltfile. The Tiltfile reads neither the catalogue nor the compose list itself; it `watch_file()`s the root `.env` and [models.json](./compose/models/models.json) so edits reload it, and `compose/n8n/.env` is on the watch list of the n8n project. The plan runs before the gate, and `watch_plan()` then `watch_file()`s the `watch` list of every project (the `.env` beside its entry file, which Tilt does not watch by itself, and the parents of the n8n cascade) before `verify()` runs: Tilt keeps the paths recorded before a `fail()`, so a `pnpm run setup` or `pnpm run secrets set` that creates or fills a `.env` reloads a Tiltfile whose gate failed by itself (a missing docker network is no file change, so reload Tilt by hand after creating it).
3. Runs `n8n-starter verify --json` ([verify.ts](./packages/cli/src/commands/verify.ts)) as a gate through `local(…, quiet=True)` with `|| true` (`local()` raises on exit 1 and cannot read an exit code) and `decode_json`s the report `{ ok, success, info, warnings, errors, hints }`: every warning becomes a `warn()` alert (an `AI_RUNTIME` that does not fit the detected platform arrives this way), and when `ok` is false the Tiltfile `fail()`s with one message listing the errors marked `❌` (a too-old or missing tool, the missing `.env` files, the unfilled or stale secrets, a required license key included, or the missing networks) and the hints marked `💡` that name the fixing root script, so `tilt up` cannot start services against an unconfigured checkout and the log shows that message instead of a traceback.
4. Clears all enabled resources, enables exactly the `enabled` ones of the plan, then loops: one `docker_compose(files [+ encode_yaml(override)], project_name, profiles)` per project (its watch list is already registered, so editing a per-service `.env` or the base of the cascade reloads Tilt while a variant is active, and on a reload Tilt re-renders every project and recreates only the services whose rendered configuration changed) and one `dc_resource(service, new_name, project_name, labels, resource_deps, links, infer_links, auto_init)` per resource. The plan mirrors the `compose/` directories: proxy (docker-socket-proxy, traefik), n8n (n8n; plus n8n-runner from `build`, n8n-worker, n8n-worker-runner and n8n-webhook in queue mode; sandbox-certs, sandbox-api, sandbox-runner-1 and searxng of `compose/n8n/assistant`, enabled by `N8N_ASSISTANT=true`), storage (postgres and pgadmin enabled from `build`; redis and redisinsight enabled in queue mode; garage and garage-webui enabled for `enterprise`), services (qdrant) and models (litellm-db and litellm enabled by `AI_GATEWAY=litellm`, with the model list as the `content` of the config `litellm-config`; ollama once as project `ollama` with the `MODELS` list, `auto_init` only when `AI_MODELS` is not empty; vllm once per model of `AI_MODELS` as project `vllm-<id>` with `MODEL`, `MODEL_ARGS` and `container_name`, the profile service registered under the resource name `ollama` or `vllm-<id>`). Every compose project is registered, so disabled services stay visible in the UI and can be started by hand. Every resource of a project with `secrets` also gets a `secrets` button (`cmd_button` of the `uibutton` extension, named `<resource>-secrets`): a click runs `n8n-starter secrets read <directory>` and prints the secrets of that project's `.env` and `.env.secrets` in plain text into the log of the resource (for n8n the owner login with it), nothing before the click. The directory is the filter because it matches that `.env` alone, also where a manifest is nested in it as `compose/n8n/assistant` is in `compose/n8n`, while a name such as `postgres` also matches the keys of other projects. These are the resources of `compose/n8n`, `compose/n8n/assistant`, `compose/storage/postgres`, `compose/storage/pgadmin`, `compose/models/litellm` and `compose/models/vllm`; a new manifest gets its button from the plan, without a Tiltfile change. The extension creates buttons only for `tilt up` and `tilt ci`, and the button of a resource that left the plan stays until Tilt restarts.
5. Re-applies the enabled set on a reload. Tilt keeps the old enabled/disabled flag of every registered resource when the Tiltfile re-executes unless `tilt args` changed ([tilt-dev/tilt#6800](https://github.com/tilt-dev/tilt/issues/6800)), and this Tiltfile takes the set from the root `.env`, not from args. So during `tilt up` (not on the first load, where nothing is registered yet, and not for `tilt down` or `tilt alpha tiltfile-result`, which run no API server) the Tiltfile runs `tilt enable --only <enabled resources already registered>` itself, which enables those and disables the rest, stopping their containers; new manifests get their flag from the plan as before. A failure of that call is a `warn()` with the command to run by hand, never a load error. This is what makes a `N8N_VARIANT` change in the root `.env` take effect while Tilt runs: `dev` → `build` starts postgres before n8n is recreated against it and adds the runner sidecar, `build` → `community` starts redis before the new worker and webhook processor, `community` → `dev` stops them again.

`dc_resource` conventions, encoded in `tiltResources()` of [tilt.ts](./packages/cli/src/commands/tilt.ts) and covered by its tests:

* `labels` group services in the Tilt UI by compose directory (`proxy`, `n8n`, `storage`, `services`, `models`).
* `links` point at the traefik hostname (`<service>.<DOMAIN>`, `DOMAIN` for n8n, `hooks.<DOMAIN>` for n8n-webhook, `litellm.<DOMAIN>/ui` for litellm, whose host root is the OpenAPI page); `infer_links=False` on services without a UI, the model servers included.
* `resource_deps` only expresses real start-order needs (pgadmin → postgres, redisinsight → redis; from `build` n8n → postgres and n8n-runner → n8n; in queue mode also n8n → redis, n8n-worker → n8n + redis, n8n-worker-runner → n8n-worker, n8n-webhook → n8n + redis; with the Assistant n8n → sandbox-api, sandbox-api → sandbox-certs, sandbox-runner-1 → sandbox-api; litellm → litellm-db, never a model server). Tilt takes a compose service as ready once its container started, so the API can start before the one-shot wrote its certificates on the very first run: its restart policy covers that, as for every start order across projects. Networks are not resources any more; `setup` owns them.
* Optional services are `auto_init=False` so they show up in Tilt but only start on demand. The ollama server is optional only while `AI_MODELS` is empty.

## n8n-starter CLI (`packages/cli`)

A small TypeScript CLI (`@bomb.sh/args` for flags, `@clack/prompts` for output and prompts, `zod` for the root `.env`, the model catalogue and the manifest schemas, `bcryptjs` for the hash of the n8n owner password, the library n8n checks it with), bundled with tsdown to `dist/index.mjs`; the dependencies stay outside the bundle, so `pnpm install` comes first. It must be built (`pnpm run build`) before the root scripts and the Tiltfile can call it.

| Command | Behaviour |
| --- | --- |
| `setup` | Create a `.env` next to every `.env.template` (never overwriting), detect the platform and write its runtime into `AI_RUNTIME` of a root `.env` created in this run (an existing one is left alone and warned about when it does not fit), fill the secrets of every `.env.json` (random values once, the ones no container reads into the `.env.secrets` beside the `.env` with a line naming `secrets read`, derived values and links set to their source, a required human secret only warned about), then create the `n8n-starter-public` and `n8n-starter-private` docker networks if missing. A run without an error signs off below its summary with the n8n logo in half blocks (the mark in the accent colour, the wordmark in the foreground of the terminal) , the line `self-hosted-ai-starter-kit ready to use` and a line naming the next steps (`pnpm run dev`, `pnpm run config`, in the accent colour); a terminal narrower than the logo gets the two lines alone. Exit code 1 when Docker is unreachable or a manifest is invalid. |
| `verify [--json]` | Read-only check that node, the docker daemon and docker compose meet `REQUIREMENTS` ([requirements.ts](./packages/cli/src/utils/requirements.ts): `node --version`, `docker version --format {{.Server.Version}}`, `docker compose version --short`; a tool that is too old or cannot be queried fails it), that every `.env` and both networks exist and that every declared secret is filled: an empty generated or linked key, a link that differs from its source, a derived value that does not match its input or a human secret the root `.env` requires fails it. The detected platform ([platform.ts](./packages/cli/src/utils/platform.ts)) is an info line and an `AI_RUNTIME` that differs from its runtime a warning that names `pnpm run config AI_RUNTIME <runtime>`, never a failure. A failed line names its fix (`pnpm run secrets set KEY` for a human secret), one hint points at `pnpm run setup` only when it creates what is missing (a file, a generated or linked secret, a network) and one at the Prerequisites of README.md when a tool version fails. `--json` prints the report `{ ok, success, info, warnings, errors, hints }` as one JSON document and nothing else on stdout. Exit code 1 when anything is missing. |
| `config [KEY] [value]` | Edit one key of the root `.env` (`N8N_VARIANT`, `N8N_ASSISTANT`, `AI_RUNTIME`, `AI_ENGINE`, `AI_GATEWAY`, `AI_MODELS`, `DOMAIN`). Without `KEY` a select lists the keys with their template description and available values, the current one in green, then only the chosen key is prompted; with `KEY` only that prompt runs; with `KEY` and `value` nothing is prompted and the value is validated, exit code 1 when it is rejected or the key is unknown. `AI_MODELS` runs `models select [ids]` under the `config` intro (chosen in the select or named as `KEY`: its multi-select, or the given ids validated against the catalogue), so both commands behave the same. `N8N_ASSISTANT` asks for the toggle and, when it is switched on, for the model: a cloud provider and one of its models from [models.cloud.json](./compose/models/models.cloud.json), or one of the models of `AI_MODELS` the engine serves (that choice is disabled while there is none); `N8N_ASSISTANT true <model>` takes an id of `AI_MODELS` or `provider/model` without a prompt, and `true` or `false` alone only flips the toggle. It is the one key that writes outside the root `.env`: `N8N_INSTANCE_AI_MODEL` and `N8N_INSTANCE_AI_MODEL_URL` of `compose/n8n/.env`, before the toggle, and it names the `secrets set` command for the key the model needs instead of writing one. Changing `AI_ENGINE` or `AI_RUNTIME` keeps `AI_MODELS` and warns about ids the new combination does not serve, and about an Assistant model it no longer serves (`AI_ENGINE` also prints where n8n reaches every selected model). `AI_GATEWAY` offers `none` first, which writes an empty value (`pnpm run config AI_GATEWAY ""` without a prompt), and prints the endpoint of the gateway it set. `AI_RUNTIME` detects the platform first: the prompt marks the fitting runtime with a green `(detected)` visible on every row, and a value that differs from it is written with a warning. Only the requested key is written; comments and other keys are preserved. |
| `models read [filter] [--json]` | Print the models of the validated [models.json](./compose/models/models.json), nothing else on stdout: one block per engine and model (a header `<engine>/<id>`, then `key=value` lines with the key in the accent colour on a tty), engines in `AI_ENGINE` order and models in catalogue order, filtered by a part of an engine or id; with `--json` the same records as an array of `{ engine, id, model, label, args?, memory?, note?, runtimes? }`. Unlike `secrets read` there is no bare-value mode, since a model has no single value to pipe. Exit code 1 naming the file when it is missing or invalid, or the filter when nothing matches. |
| `models select [ids]` | Edit `AI_MODELS` of the root `.env`: a multi-select over every model of the catalogue of the current engine (id, label, model name, `~<memory> GB RAM` or VRAM after the runtime, and the note as hint; entries the current runtime cannot run are shown disabled; skipped when none runs), preceded by the detected platform line, with an estimate above the docker memory pointed out on the CPU runtimes but still selectable, or with `ids` the comma separated ids written without a prompt (`""` clears the list), validated against the schema and the catalogue of the current engine and runtime, exit code 1 when rejected. Prints where n8n reaches every selected model, and the endpoint of the gateway when `AI_GATEWAY` is set, and warns when the selection drops the model an activated Assistant runs on. Only `AI_MODELS` is written. |
| `tilt resources` | Print the Tilt resource plan of the root `.env` as JSON, nothing else on stdout (see [Developer experience with Tilt](#developer-experience-with-tilt)). Exit code 1 with the reason when the `.env` is missing or invalid, the catalogue is invalid, an `AI_MODELS` id is not served by the engine on the runtime, or `N8N_ASSISTANT` is on with a stale model in `compose/n8n/.env`. |
| `secrets read [filter] [--json]` | Print the declared secrets of the `.env` and `.env.secrets` files as `KEY=value` lines grouped by file, each with its `related` keys above it, nothing else on stdout; `filter` keeps the keys whose directory or name contains it (the directory of a manifest keeps that directory alone), an exact key prints only its value, a derived value is listed only when named; `--json` prints one array of `{ file, key, value, source, related? }` instead. Exit code 1 when a `.env` or `.env.secrets` is missing, nothing matches or a manifest is invalid. |
| `secrets set KEY [value]` | Write one `generate` or `prompt` secret into the file it lives in, derive what is built from it and copy it to its links: `KEY` alone asks for the value with a masked prompt, `KEY value` writes without a prompt. A link or a derived key, an unknown key, an empty value or one that cannot be stored (a single quote, a backslash, a line break) exits with code 1 without writing. |
| `reset` | Delete all generated `.env` and `.env.secrets` files after confirmation, warning first about the secrets the data in `.volumes/` depends on. |

The command line is `n8n-starter <command> [sub-command] [value] [options]`: a command may take one sub-command and one value as positional arguments (`config`, whose sub-command is the key and which takes the model as a second value for `N8N_ASSISTANT`; `models` with `read` and `select`; `secrets` with `read` and `set`; `tilt` with `resources`); commands without sub-commands reject extra arguments with exit code 1, and a command that needs a sub-command called without one or with an unknown one prints the reason and its own help with exit code 1. `--help` and `help [command]` print the global help or the help of the named command with exit code 0; both renderings come from one table, [help.ts](./packages/cli/src/help.ts). Positional arguments are read as given from `argv` (never coerced, an empty string stays one). Global options apply to every command: `--log-level silent|error|warn|info|debug` (default `info`) and `-q`/`--quiet` as shorthand for `error`; `--json` is accepted by `verify`, `models read` and `secrets read` and rejected elsewhere with exit code 1. Log output goes through one level-gated logger ([src/utils/logger.ts](./packages/cli/src/utils/logger.ts)) that keeps the clack symbol per level (`◆` success, `●` info, `▲` warning, `■` error) and adds `hint` for the line that names a fix, logged at the error level under `💡` so a `--log-level error` run still prints it without showing it as an error; interactive prompts are never silenced. Every hint names the root script that fixes a problem (`pnpm run setup`, `pnpm run secrets set KEY`, …) through `runCommand()` of [src/utils/format.ts](./packages/cli/src/utils/format.ts), since the root scripts are the only documented way to run the CLI (no global install; `pnpm run cli <command> …` is the generic one for trying any command), except the tool versions, which no script installs: that hint names the Prerequisites of README.md; intros and the help keep the name `n8n-starter`. The stdout sub-commands (`models read`, `tilt resources`, `secrets read`, `verify --json`) write their output with `console.log` and nothing else to stdout, so a consumer such as the Tiltfile or a pipe can read it; the `key=value` lines of `models read` and `secrets read` colour the key only on a tty (plain when piped or with `NO_COLOR`), and their errors go through the logger like everywhere else. The highlight colour of the CLI is the n8n brand accent, the pink `#FF91AC` of the logo mark (`accent()` of [src/utils/format.ts](./packages/cli/src/utils/format.ts): the exact colour on a 24 bit terminal, the nearest entry of the 256 colour table or bright magenta below that); it marks the usage column of the help and those keys, while the prompts keep the colours of clack.

Practices inside the package:

* One file per command in `src/commands/`, shared helpers in `src/utils/` (`files`, `env`, `generators`, `docker`, `requirements`, `platform`, `models`, `assistant`, `logger`), schemas in `src/schemas/` (`config` for the root `.env`, `models` for the catalogue, `assistant` for the cloud models of the Assistant, `secrets` for the manifests, `tilt` for the resource plan). Commands export their logic (`generateEnvFiles`, `fillSecrets`, `ensureDockerNetworks`, `verifyEnvironment`, `tiltResources`, …) separately from the command function so it can be tested without the UI.
* Anything that touches the outside world is injectable: every command takes `rootDir`, and docker helpers take a `run` function, so tests use temp directories and an in-memory fake `docker` instead of a real daemon.
* Tests live in `tests/` (vitest), mock `@clack/prompts` wholesale, and are part of the TypeScript project, so `pnpm typecheck` covers them. `pnpm test`, `pnpm typecheck` and `pnpm build` must all pass.
* The CLI changes nothing it did not create: existing `.env` files and docker networks are left alone, except that `setup` fills a secret that is still empty and keeps a linked or derived secret in step with its source, and that `config N8N_ASSISTANT` writes the two model keys of `compose/n8n/.env` it was asked to set.

## Best practices

* Configurations are loaded from `.env` files that are never committed to git.
* On setup, `.env` files are generated from `.env.template` files and their secrets from the `.env.json` next to each template.
* Two docker networks, membership decided by whether traefik routes to the container.
* One compose project per service directory, pinned image versions, healthchecks, no host ports unless needed.
* The Tiltfile orchestrates; it does not create infrastructure. Infrastructure (networks, `.env` files) is created by `setup` and checked by `verify`.
* Scripts stay idempotent: `setup`, `verify` and `tilt up` can be re-run at any time without side effects on existing state.
* Markdown and file comments reference other files by a relative path from the referencing file (`../../SPEC.md` from `compose/n8n/`, `./docker-compose.enterprise.yml` from the `.env.template` next to it), so IDEs can open them with a click.
